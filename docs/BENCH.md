# Sea Benchmarks

**Status: normative** for the benchmark tools (`bench/`, `docs/DESIGN.md` §2.17): what is
measured, how, against what, and how the results are reported. §2 and §4–§8 are generated by
`make bench-report` (`bench/report.py`) from the committed files of `bench/results/p10/` and the
four MATLAB timing files; they are pasted here unchanged and no number in them was typed by hand.
§1, §3, §9 and §10 are prose.

The measurement is one session (§2): one agent ran `make bench` and `make bench-cross` in one go on
the machine that produced the MATLAB baseline (an Apple M2 Pro, `Mac14,9`) and on the Linux host
`desktop`. The pass is decided by that one measurement; results of different sessions are never
combined. This file reports what was measured, including what is awkward about it (§3.7).

## 1. What is measured, and the pass rule

**The seven workloads** (DESIGN.md §1.2): `w1_shaft_design`, `w2_truss_fem`, `w3_quarter_car`,
`w4_heat_plate`, `w5_tolerance_mc`, `w7_drivetrain` and `w8_ev_can`, each a Sea port (`ports/`)
of a MATLAB script, timed on `arm64-macos` against the MATLAB baseline recorded on the same machine
(Decision 7, and the files of DESIGN.md §1.2: `baseline_timings_matlab.json` for W1–W5,
`baseline_timings_matlab_w7_drivetrain.json`, `baseline_timings_matlab_w8_ev_can.json`).

**The two measures** (DESIGN.md §1.2, §6.5):

* **whole-process time**: the wall time from just before the process is created to just after its
  exit is collected (`spawn_time`, §3.1), so it contains everything the operating system does to
  start, load and end the program, compared with MATLAB's `total_seconds`;
* **compute time**: the one line `Compute time: %.3f s` that every port prints for the same region
  as the MATLAB script's `tic`/`toc`, compared with MATLAB's `compute_seconds`.

**The pass rule** (DESIGN.md §6.5, §5.7, §2.17.8). For every workload, Sea's best of 5
consecutive runs (the first run included) must be faster than MATLAB's best of its five runs, on
both measures, strictly; equality is a miss. Sea's wall is compared as its printed value plus
5·10⁻¹⁰ s and its compute time as its printed value plus 0.0005 s (§3.3). The machine of the
environment record must equal the machine of the MATLAB files. `bench/check.py` decides this from
the committed files alone; its output is §5. Medians and the 10 further runs are reported, never
used for the verdict.

**Reported, never judged**:

* MATLAB with one computational thread (`baseline_timings_matlab_1thread.json`, W1–W5), beside
  Sea's best of 5 (§4);
* NumPy (the cross-check scripts of `workloads/reference_py/`), timed in-process (Decision 167, §3.5;
  §4);
* the three Sea-level matrix kernels (`gemm`, `solve`, `axpby`) against Accelerate or OpenBLAS
  (Decision 162, §3.6; §6);
* the two micro-benchmarks `lcg` and `sor` against C (§7);
* the Linux x86_64 workload times on the host `desktop`, with no MATLAB columns: "reported,
  compared with nothing" (Decision 165; §8).

**What 1.0.0 means** (Decision 79, Decision 166). Every Sea version 0.y.z is an alpha; 1.0.0 is the
general-availability version and means that v1 is done as DESIGN.md §1.2 defines it, with all seven
workloads, which includes this pass rule. No tag or release procedure is required. When §5 reads
`PASS`, the version becomes 1.0.0 wherever it is recorded; that change is made by the sub-phase
after the measurement (10d, DESIGN.md §2.17.11), not by this file.

## 3. Methodology

The rules are those of DESIGN.md §2.17.3–§2.17.7; this section states them in prose, and states
first what makes the columns of §4 unlike each other (§3.1), because the comparison is "Sea against
MATLAB as users run it", not an identical-conditions contest.

### 3.1 The asymmetries

* **MATLAB ran with its default thread count, 10 threads** (`maxNumCompThreads` = 10), as the pass
  baseline was recorded (Decision 7). **Sea is single-threaded** (it has no multithreading in v1).
  The pass comparison therefore favours MATLAB wherever its BLAS and LAPACK calls can use several
  cores. The single-threaded MATLAB table in §4 is reported beside Sea's best of 5, not compared;
  on it Sea is slower than MATLAB on W2 (the two ratios of that table, below 1).
* **MATLAB's times are in-session**: the script ran inside an already running MATLAB, and MATLAB's
  start-up is excluded from `total_seconds`; the first run includes its JIT warm-up. **Sea's
  whole-process time is a whole process**: it contains the process creation, the loading of the
  binary, the run and the exit. So Sea's whole-process time pays for something MATLAB's does not,
  and the comparison is still in MATLAB's favour on that point. The compute times are the like
  measure: both are the printed time of the same `tic`/`toc` region.
* **NumPy is timed in-process with its default threads.** `bench/numpy_time.py` times the whole
  `main()` of each cross-check script inside a running interpreter with NumPy already imported:
  its computation, its JSON export and its printing (the final flush is inside the timed region).
  No thread variable is set (Decision 172), and NumPy's BLAS and thread settings are recorded in §2.
  That time is comparable in kind with MATLAB's in-session `total_seconds`, which is why §4 divides
  NumPy's best by MATLAB's best and never by Sea's whole-process time. There is no NumPy compute
  time: the scripts have no `tic`/`toc` region. Only the Mac has a NumPy or MATLAB column.
* **Different roles of the first run.** Sea's run 1 is a cold run (nothing ran the port between its
  build and run 1); MATLAB's and NumPy's first runs are in-session. The pass rule includes run 1 in
  the best of 5, as the MATLAB baseline's best includes its first run.
* **The vendor libraries are the bar, not part of Sea** (§3.6). Accelerate on the M2 Pro can use
  Apple's matrix hardware, which hand-written NEON code cannot, so "% vendor" there is not a
  like-for-like contest; on Linux the vendor library is OpenBLAS, which uses the best SIMD of the
  CPU.

### 3.2 Whole-process time, compute time and the runs

`bench/spawn_time` (C) `chdir`s to the run directory, redirects the child's standard output,
standard error and standard input, reads `clock_gettime(CLOCK_MONOTONIC)` immediately before
`posix_spawn` and immediately after `wait4` returns, and prints `wall` and the child's user + system
CPU time (`cpu`) and status. For each workload the runner makes **15 consecutive runs** with
nothing between them but their setup (a fresh run directory with the fixtures copied in, outside the
timed region), each as `PORT --export-reference` (the reference export on, the figures off, as
DESIGN.md §1.2 requires): runs 1–5 are the pass set, runs 6–15 are ten further runs. On Linux this
is done for each of the variants `avx2` and `sse2`.

Each port is built once before the measurement (`bench/workloads.sh build`), so no compiler runs
between the start condition and the last timed run; compile times are reported in §4 and never
counted. The compute time of a run is the number of its `Compute time` line exactly as printed,
with three decimals.

**What §4 and §8 print** per workload: the first run; the best of 5 (the minimum of runs 1–5); the
median of 5; the median of the 10 further runs with their minimum and maximum. The median of 10 is
the mean of the 5th and 6th smallest, computed exactly in decimal, so it has one more decimal than
the values it comes from. MATLAB's first, median and best are read from its files.

**Every timed run is checked** (so no fast wrong run can be reported): status 0, an empty standard
error, exactly one `Compute time` line, exactly the expected files in the run directory; runs 2–15
must equal run 1 byte for byte (the JSON, and the standard output without the `Compute time`
line); and run 1 is judged by `compare.py` and `compare_report.py` against the MATLAB reference,
as acceptance judges it. The driver writes no result file when any check fails.

### 3.3 The printed decimals and the pass check's two margins

The whole-process times are printed by `spawn_time` with nine decimals, the compute times by the
ports with three. A printed value stands for any real time that rounds to it, so the pass check
adds the largest rounding error before comparing: Sea's wall `wu` = the printed best + 5·10⁻¹⁰ s
(nine decimals) and Sea's compute `cu` = the printed best + 0.0005 s (three decimals). The
comparison `wu < Mt` and `cu < Mc` is strict, with MATLAB's bests `Mt`, `Mc` at full precision. A
workload passes only if it passes with the margin added. This is why the lines of §5 print values
such as `0.0390040005` and `0.0285`: they are the values actually compared, not the printed ones.

### 3.4 The start condition and the preconditions

Before each tool's measurement in final mode, `bench/settle.sh` sleeps 120 s (the cool-down after
the build or the previous tool), then reads the 1-minute load average every 10 s until it is at
most 2.0; if it has not fallen to 2.0 within 15 minutes of the end of the cool-down, the driver
stops without measuring (Decision 170). The seconds waited after the cool-down, and the three load
averages just before the first and just after the last measured process, are recorded for every
tool and printed in §2 as "Start-condition wait", "Load before" and "Load after". The limit is 2.0
rather than 1.0 because an idle Mac with an agent session open showed 1.68–2.28 (Decision 170).

Preconditions of a final run (a failure is a setup error, exit 2, nothing measured): the driver is
unniced; the Mac is on AC power and Low Power Mode is off; the Sea working tree and the Baysick
checkout are clean, so the measured binaries are those of the recorded commits; the build is not
stale; no override of the ports or kernels directory is set; and each tool runs once per session
(an attempt marker is created before the start condition). No measured process is niced, given a
QoS class or pinned to a CPU, on either system, for every implementation alike (as the MATLAB
baseline ran). Because a process started from an agent's shell may still inherit a lowered
scheduling class, each workload run's CPU time is recorded beside its wall time, and `report.py`
flags a run whose user + system CPU time is below 0.8 × its wall time as one that waited for a CPU
(§4, "Runs that waited for a CPU").

The environment of measured processes: `SEA_HEAP_CHECK` and `BAYSICK_KERNELS` are removed;
`SEA_KERNELS` is removed on the Mac and set to the measured variant on Linux; the kernel and
micro-benchmark runs use one vendor thread (`VECLIB_MAXIMUM_THREADS=1` on the Mac,
`OPENBLAS_NUM_THREADS=1` on Linux); the NumPy and workload runs get no thread variable; standard
input is `/dev/null`; `LC_ALL` is unset for measured processes.

### 3.5 NumPy

`numpy==2.5.4` is pinned and run through `uv`. For each workload, `numpy_time.py` makes 5 runs in
one process; before each, outside the timed region, it points the script's output at a scratch
directory (so the committed reference files are never written) and file descriptor 1 at a file.
After the last run it checks run 1 of every workload against the reference with `compare.py`'s
NumPy mode and runs 2–5 byte for byte against run 1. Reported: first, median of 5, best of 5, and
the ratio of the best to MATLAB's best `total_seconds`. The column is reported, never judged.

### 3.6 The Sea-level kernel benchmarks

Three programs written in Sea (`bench/kernels/gemm.sea`, `solve.sea`, `axpby.sea`) measure what a
Sea user gets from `@`, `solve` and a fused element-wise expression, against the vendor library and,
for the fused loop, a C loop. Their text is fixed by DESIGN.md §2.17.6.

* **The protocol.** Each executable takes `N BATCH`, builds its data untimed, makes one untimed
  warm-up call, then `BATCH` timed calls back to back with a monotonic clock. **Before call r it
  changes one input by r mod 2**, inside the timed region, so no call computes what the previous one
  did and the last call's result depends on its own input; the printed `check` line comes from
  the last call and is validated against exact expected values (`gemm`, `axpby`, computed
  independently in `int64_t`) or a bound (`solve`: at most 1·10⁻⁹).
* **Calibration and repetitions.** The runner finds a reference batch (b grows ×4 from 2, at most
  100 000, until the minimum per-call time times b is at least 10 µs), sets `BATCH` so that a
  process makes about 5 ms of timed calls (at least 1, at most 100 000), and then runs one
  process per repetition until at least 5 repetitions and at least 1.0 s of timed calls, at most 200.
  The median per-call time is reported with the minimum and maximum (in the TSV). Rates are work
  over the median time in 10⁹ units: 2N³ flop for `gemm`, (2/3)N³ + 2N² flop (nominal) for `solve`
  (GFLOP/s), 24N bytes for `axpby` (GB/s).
* **What the times include.** Every implementation's time includes the per-call input change.
  The Sea times include what the Sea expression does and the vendor call does not: `@` may allocate
  its result on each call, and `solve` copies `a` (it does not change its argument). The vendor's
  `solve` includes its own two copies of `a` and `b` for the same reason (`dgesv` overwrites them).
* **The vendor rows.** Mac: Accelerate (`cblas_dgemm`, LAPACK `dgesv_`, `vDSP_vsmsmaD`), one thread.
  Linux: OpenBLAS (`cblas_dgemm`, `dgesv_`), one thread, linked and checked through
  `openblas_get_config()` so a reference BLAS is never accepted. **The `vendor-proxy` row**: OpenBLAS
  has no fused `w = 0.75x − 1.25y`, so its `axpby` row is the two-pass proxy `cblas_dcopy` then
  `cblas_daxpby`, labelled `vendor-proxy` in the TSV and in §6. A `% vendor` above 100 on that row
  therefore compares a fused one-pass loop with a two-pass proxy; the `c-O2` column (the same loop in
  C) is the like-for-like reference.
* **Accelerate's matrix hardware.** On the Apple M2 Pro, Accelerate's `dgemm` and `dgesv` can use
  Apple's matrix hardware, which hand-written NEON code cannot use, so the Mac `% vendor` of `gemm`
  and `solve` is not a like-for-like contest. No instruction-set peak is measured.
* **The guard's window, stated honestly** (DESIGN.md §2.17.6). A single call cannot be timed
  reliably: macOS's `CLOCK_MONOTONIC` ticks in 1 µs, the two clock reads cost more than an `axpby`
  of 1 000 elements, and the first timed call of a process can cost about twice the later ones.
  Hence the batching and the reference batch. The check that a batched call is not more than twice
  as fast as the reference (a sign of skipped or merged work) has a window: kernels whose `BATCH` is
  at most the reference batch (calls of about 2.5 ms and more, `BATCH` 1 or 2) are not guarded by
  it; a program that skips all but the last call would escape wherever its real call costs less
  than 10 µs (`axpby` N = 1 000, for example); it is caught where its call costs at least 10 µs and
  `BATCH` exceeds twice the reference batch (from `axpby` N = 100 000 and `gemm` N = 64 up to calls
  of about 1 ms). Outside the window the per-call input change and the check line still hold. The
  TSV's `batch` column shows which rows are in which part; the programs measured here are the
  natural loops of DESIGN.md §2.17.6, and the injected skips of 10b were caught inside the window on
  both platforms.
* **Variants.** The `sea` rows are measured on the Mac with the one variant `neon` and on Linux
  with `SEA_KERNELS=avx2` and again with `SEA_KERNELS=sse2`; the `vendor`, `vendor-proxy` and `c-O2`
  rows have the variant `-`. The C files are measuring instruments built with `-O2
  -ffp-contract=off`; every timed call goes through a `noinline` function whose body ends in an
  empty `asm volatile` with a `"memory"` clobber, so the compiler can neither merge nor hoist calls.

### 3.7 The micro-benchmarks, and what to be careful of

`lcg` (11 000 000 steps of W5's generator) and `sor` (W4's scalar SOR loop) are Sea programs
with C references, compiled by the compiler at the measured commit (label `sea-p10`), measured by
Baysick's rules: warm-up, at least 5 repetitions and 1 s, the median with minimum and maximum. They
are two scalar loops, not the workloads. §7 prints the final-session rates; the phase-5 table, with
the phase-4 compiler, is DESIGN.md §5.9.

Things a reader should know about this measurement:

* **The load average after the Mac workloads was 2.41** (the second field of "Load after" for the
  `workloads` tool in §2), above the start condition's limit of 2.0, so `check.txt` (§5) carries
  the line `warning: load average above 2.0`; the warning changes no verdict. **The start condition
  itself was met before the run**: the 1-minute load average before the workloads was 1.72
  (§2), at most 2.0, so no wait was needed (the start-condition wait of that tool is 0 s), and the
  later Mac tools waited as §2 records. Every record says nice 0, `power` `ac` and `lowpower` 0 on
  the Mac, and the load averages after the later tools are in §2 too. The Mac was not an idle
  laboratory machine: its load averages before the tools are 1.72, 1.95, 1.90 and 2.00 on the
  1-minute field (§2), the start condition's limit being 2.0.
* **Run 1 of every Mac workload is flagged** in §4 ("Runs that waited for a CPU"): its CPU time is
  below 0.8 × its wall time. Run 1 is the cold run (nothing ran the port before it), and the flag
  is what that rule shows for it; the files do not say more about the cause. The flag is
  reported, not an exclusion: the pass rule's best of 5 and every other column are computed from all
  runs as recorded, and none of the flagged runs is dropped.
* **MATLAB's baseline is not re-run here.** Only the user runs MATLAB (Decision 7); its files
  were committed before the measurement, and no number of this session was produced for it.
* **The kernel guard has a window** (§3.6): rows with `BATCH` 1 or 2, and `axpby` N = 1 000, are not
  protected by the twice-as-fast check. The input change and the exact check line apply everywhere.
* **A kernel rate is work over the median per-call time of the repetitions**, not a peak; the
  `solve` rate uses the nominal flop count of an LU solve for both implementations.

## 9. Reproducing

Every target is run from the Sea repository on the Mac (`sea/`), depends on `all`, and is no part of
`make test`, `make cross` or any CI. The Baysick checkout (the parent of `sea/`) must be built
first (`make -C ..`); the Linux half needs ssh access to the host (default `desktop`; `make
bench-cross BENCH_CROSS_ARGS='-H HOST'`) with GNU `as`, `gcc`, `make` and OpenBLAS with its
`cblas.h` and LAPACK symbols, and a CPU that lists `avx2`.

| Target | Runs |
|--------|------|
| `make bench-session` | creates the session directory and its `session.txt` |
| `make bench-build` | builds everything the measurements run (ports, kernel programs, vendor harness, C references, micro-benchmarks) and measures nothing |
| `make bench-workloads` | the 15 runs of each workload (§3.2) |
| `make bench-kernels` | the Sea-level kernel benchmarks (§3.6) |
| `make bench-micro` | the micro-benchmarks of the current compiler (§3.7) |
| `make bench-numpy` | the NumPy column (§3.5) |
| `make bench-check` | `bench/check.py`: the pass check, written to `check.txt` |
| `make bench` | the session, the build, then workloads, kernels, micro-benchmarks and NumPy, then the check (final mode) |
| `make bench-cross` | the workloads, kernels and micro-benchmarks on the Linux host, into the session of the same directory |
| `make bench-report` | `bench/report.py`: the Markdown of §2 and §4–§8 of this file |
| `make bench-selftest` | the self-tests of `spawn_time` and of `check.py` |

`BENCH_OUT` (default `bench/results/p10`) chooses the results directory, `BENCH_QUICK=1` makes a
smoke run (fewer runs and sizes, no start condition, its records say `mode quick`, which the pass
check refuses).

**Preconditions of the final measurement** (DESIGN.md §2.17.3, §2.17.10): `make all` done; the Sea
working tree and the Baysick checkout clean; the results directory absent or empty; the driver's own
shell unniced (zsh's `BG_NICE` gives a background job nice value 5, so start the run in the
foreground, or through `/bin/sh -c '… &'`); on the Mac, AC power and Low Power Mode off; `uv run
--no-project --with numpy==2.5.4 python -c 'import numpy'` working; `ssh -o BatchMode=yes desktop
true` succeeding; no other work started on the Mac meanwhile. A result file is written once per
session and never replaced; a tool stops with exit 2 on any precondition, on a stale build, or on
the start condition's timeout, and is then not retried within the session.

The results of a measurement are committed under `bench/results/p10/`. A failed attempt would be
kept: before a re-measurement the directory is moved to `bench/results/p10-attempt-K/`, so the new
session starts in an empty `bench/results/p10/`. `make bench-report` regenerates §2 and §4–§8 from
the committed files and prints nothing it did not read from them; `make bench-check` rewrites
`check.txt` with the same content, since the check is deterministic on the committed files.
